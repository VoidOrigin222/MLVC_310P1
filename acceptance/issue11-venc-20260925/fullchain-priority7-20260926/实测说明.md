# 转换流优先级 A/B 实测

日期：2026-09-26。测试设备为 Ascend 310P1 解码端；每轮均使用同一编码端配置、同一 537 帧输入、同一模型、队列深度和 VENC/RTSP 路径。每种优先级各跑两轮，轮次间没有并行任务。

## 变更与验证范围

只调整 FP16 YUV444→NV12 转换 ACL stream 的优先级。310P1 上查询到优先级范围为 `least=7, greatest=0`，普通 `aclrtCreateStream` 查询结果为 0，因此 7 是最低优先级。实验调用为 `aclrtCreateStreamWithConfig(&convert_stream_, 7U, 0U)`，flag 保持 0。

候选程序在隔离的板端副本编译和运行，没有覆盖原部署项目或其构建产物。本地 [decode.cc](../../../application/src/stream/mlvc/decode.cc) 已保留该单行设置。

## 全链路结果

| 转换流优先级 | 解码 FPS（两轮） | 平均 FPS | 设备解码帧 | VENC 发布 | 发布端丢帧 |
|---|---:|---:|---:|---:|---:|
| 默认 0 | 29.8693 / 29.7991 | 29.8342 | 537/537 | 537/537 | 0 |
| 最低 7 | 30.0744 / 30.0604 | 30.0674 | 537/537 | 537/537 | 0 |

优先级 7 平均快 **0.233 FPS（约 0.78%）**，两轮均超过 30 FPS。NPU AICore 只统计有负载期间样本（剔除开始/结束时的 0% 空闲样本）：默认优先级平均 **86.66%**，优先级 7 平均 **90.14%**；峰值分别为 **90%** 和 **91%**。

537 帧 trace 的平均阶段耗时：

| 阶段 | 默认 0 | 最低 7 | 变化 |
|---|---:|---:|---:|
| `MLVCDecoder` pipeline 阶段 | 31.886 ms/帧 | 31.644 ms/帧 | -0.242 ms |
| FP16→NV12 device 转换 | 12.777 ms/帧 | 12.825 ms/帧 | +0.048 ms |
| DVPP VENC 路径 | 20.084 ms/帧 | 20.431 ms/帧 | +0.348 ms |
| rANS 解码 | 15.392 ms/帧 | 15.190 ms/帧 | -0.202 ms |

结论：较低转换优先级让出了一些 NPU 调度空间，`MLVCDecoder` 阶段有约 0.24 ms/帧的小幅改善；它没有降低转换自身耗时，整体收益有限，但两轮结果方向一致并达到 30 FPS。转换优先级不应被当成大幅提速手段；下一步收益更可能来自 `MLVCDecoder` 模型内部的算子级 profiling/优化。

## 客户端收帧说明

设备日志每轮均显示 VENC 发布 537 帧、`forward_dropped_frames=0`。PC 侧 RTSP 探针本轮报告 486–509 帧，未能证明客户端收到全部 537 帧；这是独立的 RTSP 接入/收帧验证问题，不将板端发布数等同于客户端收全帧。

各轮结果 JSON、trace 和 NPU 采样保留在本地验收目录，未纳入 GitHub 版本；四轮 trace 汇总为 `profile-comparison-4runs.json`。
