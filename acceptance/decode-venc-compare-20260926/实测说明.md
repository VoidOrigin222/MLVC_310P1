# 解码吞吐对照（2026-09-26）

## 测试条件

- 解码端：Ascend 310P1；测试源码在隔离目录以 Release 模式构建，未覆盖板上原工程。
- 输入：同一份 537 帧 1080p MLVC 码流，SHA-256 为 `54a8dcb9bdac3a1972923ebbddaa1fffc66de3c784913790ed07026fe16fc0bd`。
- 解码模型、`entropy_workers=2`、队列与图包配置均相同；两种模式都完成 537 帧。

## 吞吐结果

| 模式 | 解码吞吐 | 结果 |
| --- | ---: | --- |
| DVPP VENC + RTSP | 30.0216 FPS | `537/537`；RTSP 发布 537 帧；板端转发丢帧 0 |
| 不启用视频输出 / VENC | 42.7455 FPS | `537/537`；`output_transport_mode=none` |

无输出基线比 VENC+RTSP 高 42.38%；开启 VENC+RTSP 后吞吐低 29.77%。这两项分别代表“完整 VENC 输出路径”和“纯解码基线”，不是软件编码与硬件编码的等负载对照。

另尝试了 `output_transport_rtsp_encoder="libx264"`，但板上的精简 FFmpeg 是 `--disable-everything` 构建，`ffmpeg -encoders` 为空；软件 RTSP 路径因不识别 `-preset` 而未启动。因此本次没有得到“软件 libx264 RTSP”的 FPS。错误记录见 `libx264-startup-error.log`。

PC FFmpeg 收到 498 帧；解码程序自身记录 RTSP 发布 537 帧且 `forward_dropped_frames=0`。客户端统计少于板端发布数，不作为解码丢帧结论。

## Trace 观察与优化方向

Trace 中，VENC 模式的 `MLVCDecoder` ACL stage 平均约 32.01 ms/帧；无输出模式约 23.09 ms/帧。VENC 路径还记录到 NV12 转换约 12.78 ms/帧、`dvpp_venc.h264_mpi_encode_d2h` 整段约 20.19 ms/帧。事件有并行/重叠，不能简单相加当作帧延迟，但两条路径都接近 30 FPS 的临界区。

1. **VENC 通道生命周期已实测。** `DvppH264Encoder::EncodeDevice()` 在首帧后每帧调用 `RestartChannel()`，见 `mlvc/src/io/dvpp_h264_encoder.cc`。移除该调用的独立试验在第 2 帧返回 `HI_ERR_VENC_ILLEGAL_PARAM`，所以当前 MPI 版本必须保留重建通道；详见下方试验记录。
2. **FP16 YUV444→NV12 已优化。** 通过自定义算子向量化 FP32 转换与 UV 行累加，并用 ACL 正确性测试验证；DVPP VPC 不支持直接输入 FP16，吞吐结果见下方试验记录。
3. **不要先增加队列深度。** `rtsp.venc_slot_wait` 平均约 0.002 ms/帧，`rtsp.output_enqueue` 约 0.96 ms/帧，现有 slot 等待不是主要耗时。VENC 与转换事件已和解码 stage 并行，值得检查它们是否争用设备计算资源。
4. **完整帧 D2H 已被跳过。** trace 记录跳过约 10.10 GB 的 `x_hat` D2H，实际通用 ACL D2H 为 0；进一步优化应优先看 NV12 转换、MPI VENC 生命周期与码流取回，而不是恢复整帧 CPU 镜像。

原始配置、日志和 Chrome trace 保留在本地验收目录，未纳入 GitHub 版本；`profile-summary.json` 是本地汇总产物。

## 2026-09-26 优化试验结果

### VENC 通道跨帧复用

在隔离的板端实验副本中移除
`mlvc/src/io/dvpp_h264_encoder.cc:83` 的 `RestartChannel()`，保持通道跨帧存活，使用同一
1080p FP16 输入运行 `benchmark_dvpp_h264 --frames 2`。第 2 帧提交失败：

```text
hi_mpi_venc_send_frame failed at frame 1 (..., ret=-1610055677)
```

`-1610055677 == 0xA0088003 == HI_ERR_VENC_ILLEGAL_PARAM`。因此当前 310P1/CANN 9.1
MPI 不接受本工程的连续帧提交；生产代码保留逐帧重建通道，未把失败试验改动带回主代码。

### FP16 YUV444→NV12 向量化

DVPP VPC 的 `hi_vpc_pic_info` 只有 8-bit `hi_pixel_format`，没有 FP16/位宽字段；当前输入
是 `[1,3,H,W]` 的 `DT_FLOAT16`，不能直接交给 `hi_mpi_vpc_convert_color*`。因此没有强行增加
一条先量化再 VPC 的路径（那会改变舍入语义并增加一次转换）。

在 `custom_ops/mlvc_prior_ops/op_kernel/mlvc_fp16_yuv444_to_nv12.cpp` 中将 Y 平面的
FP16→缩放→clamp→RINT 改为 AscendC 向量指令，UV 平面先向量化两行 FP32 累加，再保留最终
交错写入；输出仍与标量参考逐字节一致。板端 ACL 正确性测试通过：

| 算子版本 | 1080p 平均 | 事件耗时 |
| --- | ---: | ---: |
| 原版本 | 12.3416 ms | 12.2580 ms |
| 向量化版本 | 7.98403 ms | 7.91052 ms |

同一 `mlvc_decode`、同一 537 帧码流、同一 VENC+RTSP 配置的端到端结果为 **33.7699 FPS**
（原版本 **30.2236 FPS**），两次均 `537/537`、`forward_dropped_frames=0`；转换约减少
35.3%，端到端约提升 11.7%。向量化自定义算子仅在实验包中加载，未覆盖板端原部署包。

### 同一工作区 A/B 复测

随后在解码板上用同一个 `mlvc_decode` 二进制、同一输入码流（SHA-256 仍为
`54a8dcb9bdac3a1972923ebbddaa1fffc66de3c784913790ed07026fe16fc0bd`）、同一 VENC+RTSP
配置重新对比。分别通过 `MLVC_PRIOR_OPAPI_LIB` 和 `ASCEND_CUSTOM_OPP_PATH` 显式加载原版包与
向量化实验包；没有安装或覆盖板端原部署包。

| 算子包 | 解码吞吐 | 完成情况 |
| --- | ---: | --- |
| 原版包 | 30.1909 FPS | `537/537`；RTSP 输出 537 帧；转发丢帧 0 |
| 向量化实验包 | 33.9026 FPS | `537/537`；RTSP 输出 537 帧；转发丢帧 0 |

这次配对复测提升 **3.7117 FPS（12.29%）**。配置分别命名为
`decoder-dvpp-rerun-baseline.toml` 和 `decoder-dvpp-rerun-vector.toml`；原始配置和 trace
保留在本地验收目录，未纳入 GitHub 版本。
