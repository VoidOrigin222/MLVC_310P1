# V0.5 RTCP 与码率自适应提案

日期：2026-11-25。状态：已完成首版本地实现、两板隔离部署和有限帧验证，正式运行目录尚未切换。第 2～8 节保留实施前的设计依据，实现说明见第 10 节，最新板上结果见第 11 节。长期失联/量化饱和后的暂停策略仍待确认，当前只报告状态并保持正值限速。
从统一命名开始即为 V0.5，本工作继续属于 V0.5。

## 1. 范围与目标

用户已明确：**只控制编码板与解码板之间的直接通信，与 PC 无关。**

- 编码板到解码板：ulbvc 视频、对应检测信息、RTP/UDP/IP 开销、重传、该方向 RTCP。
- 解码板到编码板：RTCP 统计、反馈和控制，独立计量反向流量。
- PC 原图预览、PC UI、PC 对照流均不纳入预算，也不调整其配置。
- 保留 1920×1080 相机和编码、720P 逐帧检测；检测信息与图像按帧绑定。
- 先完成 310P 以太网 UDP/IP 路径；串口和 TSN 仍属后续工作。
- 用户确认暂用 2 Mb/s；本提案按正向初始/最大通信预算均为 2000000 bit/s 设计，
  反馈发现链路能力下降时允许下调，不将 2 Mb/s 当成任何时刻都能达到的保证。
- 用户确认带宽不足时降低当前代码的 `qp` / `q_index`。本轮只通过量化档位降低码量，
  不把自动降帧或降分辨率作为默认退化手段；优先维持原定帧率和帧同步。
- 用户确认发送排队上限可配置，默认 200 ms；该参数不是完整端到端延迟或每帧固定等待时间。

目标是让发送负担随链路条件变化，在用户给定的码率、画质和延迟边界内工作。
30 FPS 是链路能力与画质边界允许时的目标，不承诺任意低带宽下仍保持全帧率。

| `application/src/stream/ulbvc/encode.cc` | 消费控制消息；运动补偿开启时限制强制随机访问 | 编码边界应用码率更新；运动预取与 I 帧恢复统一调度 |

实施前正式配置固定 `qp = 11`，发送 pacing 为 2000000 bit/s，未启用目标码率控制。
因此 2 Mb/s 目前是发送限速值，不是实际可用带宽的测量结果，也不代表编码输出恒为 2 Mb/s。

必须注意以下现有语义：

1. 码率模型为 `bpp = alpha * exp(-beta * q_index)`，参数中的 beta 为负。
   模型预测是档位越大、码量越大。不能套用传统 H.264 的 QP 方向；实际调档方向和
   画质范围须用板上样片标定，界面与日志明确写 `q_index`。
2. `UdpPacer::UpdateRate()` 虽已存在，但没有贯通发送器和应用的动态更新入口。
   **pacer 的 0 表示不限速，codec target 的 0 表示不启用码控，均不是停发。**
   自适应中的暂停必须用独立状态，不能把 0 写入 pacer 当作暂停。
3. 固定档位覆盖当前会在 `SolveQIndex()` 后生效。进入自动模式时必须显式清除覆盖。
4. 现有 `ApplyControl()` 对不认识的 TLV 可能不处理却返回成功。新控制必须严格验证
   类型、长度、范围、模式组合与生效帧，未知命令明确拒绝，不能伪装已经生效。
5. codec rate controller 保存了逐帧权重，但熵编码/输出最多存在两帧在途反馈。
   后续帧的求解可能覆盖先前帧的控制上下文，不能直接打开开关就认为闭环已经可靠。

## 3. 建议架构

```mermaid
flowchart LR
    A[编码与量化档位] --> B[RTP pacing 与有界发送队列]
    B --> C[解码板接收与解码]
    C --> D[RTCP 接收统计与状态反馈]
    D --> E[编码板带宽判断与目标码率控制]
    B -->|本地队列与发送统计| E
    E -->|codec 目标码率| A
    E -->|RTP wire 发送预算| B
```

解码板负责准确测量和反馈；编码板作为唯一的码率决策方，统一更新编码目标和发送限速。
避免两端各自调节同一参数产生振荡。人工设定上限始终高于自动探测结果的优先级。

提供三个明确模式：

- `fixed_q`：保留当前固定档位行为。
- `target_rate`：编码器跟踪人工给定的固定目标码率，用于先验证模型与控制器。
- `adaptive_rate`：根据链路反馈动态更新目标，受人工最小/最大值和画质范围约束。

模式切换必须有 ACK/Reject 和实际生效帧号；进入自动模式不能残留固定档位覆盖。
网络硬限速和队列边界在三种模式下都有效，不因人工固定画质而失效。

## 4. 码率预算口径

建议业务配置给出编码板到解码板的 **IP 层总发送预算**，单位统一 bit/s。
IPv4 下包括视频/检测/媒体封装、RTP、UDP/IP、重传及同方向 RTCP；不含以太网前导码、
帧间隙等 L2 物理开销。未来串口/TSN 另由链路适配器计算对应开销。

codec 可用预算 = 正向总预算 - 检测/媒体封装开销 - RTP/UDP/IP 开销
                 - RTCP 预算 - 重传预留。

重传预留是可借用的发送余量，不要求空闲时生成填充数据。窗口内用真实发送计数修正估计。
检测信息必须计入预算，不能只看熵编码 payload；也不能把同一份 metadata 在多个统计层重复扣除。
当最低画质的码流或仅检测信息就无法装入预算时，明确进入过载策略，不能无限积压。

反向 RTCP 有独立统计与限额。保留小比例、受限的反馈带宽，不能让重传或控制报文绕过链路预算。
用户已确认暂用 **2 Mb/s**。按正向初始/最大预算均为 2 Mb/s 设计，拥塞时降低目标预算和
`q_index`，恢复时在 2 Mb/s 上限内缓慢回调。它是预算上限，不要求静态画面填满 2 Mb/s。
原先的 256 kb/s / 1 Mb/s / 2 Mb/s 试验建议不再作为当前方案。
最低可用预算由最低量化档位、检测及协议开销标定，不擅自设置一个保证可用的码率下限。

## 5. 反馈与控制规则

保留标准 SR/RR 和现有 APP envelope，能力协商成功后启用扩展状态反馈。
首期采用双方自定义 APP 状态扩展实现闭环；TMMBR 当前只有编解码基础，不能声称已经实现
完整 TMMBR/TMMBN 协商。首期不引入完整 WebRTC/GCC 栈。

反馈至少包括会话标识、递增反馈序号、统计窗口、媒体 SSRC、扩展 RTP 序号、唯一接收字节数、
首次发现的缺口、修复和重复统计、最近完整帧/已解码帧及解码积压。迟到、乱序和重传分别计数。
接收速率不等于可用带宽，不把空场景下的低发送速率判断为带宽不足。

发送端结合有效 RR、匹配的 SR/LSR/DLSR、接收窗口与自身发送队列判断拥塞。
RTT 使用匹配记录和本地单调时钟推导；不直接相减两块板的绝对时间，不要求板卡时钟同步。

初始建议值，均可配置、需要模拟和实机校准：

| 参数 | 建议起点 |
| --- | --- |
| 统计窗口 | 1 秒滑动窗口 |
| 扩展反馈 | 约每 500 ms，受反馈带宽预算限制 |
| 控制检查 | 每 200 ms，有新有效反馈才作网络判断 |
| 拥塞后调节 | 快速降低预算；初始可按 20%～30% 降幅验证 |
| 恢复策略 | 连续稳定后小步增加，逐步探测，不立即恢复到最大值 |
| 正常发送排队上限 | **已确认：可配置，默认 200 ms**；沿用 `output_transport_max_queue_delay_ms` |
| RTCP 失联候选策略 | 3 秒停止升码并降至保底；持续 10 秒无法确认接收则暂停媒体并保活 |

发送队列沿用已有配置项，实施后的默认示例为：

```toml
output_transport_max_queue_delay_ms = 200
```

实施时将 CLI、选项结构和相关发送器默认值统一为 200 ms，显式配置可覆盖。
实施前缺省值为 1000 ms；本地实现已统一为 200 ms。
该值限制发送队列积压，不强制每帧等待 200 ms，也不包含相机采集、检测、编解码和显示时间。
拥塞控制检查周期也是 200 ms 只是初始工程建议，与用户确认的队列上限是两个独立参数。

500 ms 是本项目扩展反馈的目标，不是将所有标准 SR/RR 固定改成 500 ms。
反馈采用明确协商的应用配置/调度并受限额管理；不把任意加快标准 RTCP 当作天然符合协议。
标准依据：[RFC 3550](https://www.rfc-editor.org/rfc/rfc3550.html)、
[RFC 4585](https://www.rfc-editor.org/rfc/rfc4585.html)。

应用受限时保留带宽上界信息，不能因画面静止、编码码量很小而让预算不断下降。
对高随机丢包、接收端解码过慢和网络拥塞作不同标记，不能只凭丢包率就反复降档。
长期无反馈和持续拥塞需要明确停发边界；候选策略参考
[RFC 8083](https://www.rfc-editor.org/rfc/rfc8083.html)，不声称上述简化定时值已实现完整标准算法。

## 6. 帧边界、流水线与同步

- RTCP 线程只写入经过验证的快照/命令队列；codec 状态仅由编码线程在帧边界修改。
- 发送线程拥有 pacer，通过消息/原子快照应用新限速；不跨线程直接改内部变量。
  队列准入、发送限速与日志使用同一代预算，限速变更唤醒等待队列。
- rate controller 增加运行中设置目标的接口，重配 bucket 时保留必要历史，不每次重新构造模型。
- 每帧保存决策上下文：frame ID、帧类型、档位、预算代次、权重和预留 bit；完成后按同帧实际
  大小回填差额。旧代在途帧仍正确结算，不与新帧混淆，也不为等反馈每帧排空整个流水线。
- 普通码率/档位变更不要求每次发 I 帧。沿用现有每帧模型档位和参考信息，解码使用对应帧参数。
- 本轮欠带宽先降低 `q_index`，原始代码范围为 0～63，具体有效/可接受画质范围需标定。
  不自动降帧或降分辨率，也不随机丢已编码的 P 帧分片破坏后续参考链。
- 达到最低有效档位仍超过预算时，明确报告欠带宽/量化饱和；继续降码已不可行，不能靠无限
  排队假装保持实时。其告警/暂停方式仍需确认，不把“只调档位”解释成任意低带宽都能维持 30 FPS。
- 如后续另行允许节流，应在分配编码帧与准备运动/检测之前以整帧为单位处理，并保留真实
  媒体时间与帧 ID 的对应。任何舍弃都包括同帧检测信息；参考链受损时进入随机访问恢复。

## 7. 断线与恢复

RTP 和 RTCP 分别维护存活状态。RTCP 暂时消失不等于 RTP 必然已经断开；长期无反馈如何处理
属于需要用户确认的产品取舍。暂停通过独立状态实现，RTCP 保活/握手仍可发送。

恢复不能只删除当前运动补偿保护条件。当前运动预取可能已计算之后几帧，强制 I 帧必须选择
一个尚未准备运动的安全边界，协调有界队列、H.264 运动代理、codec 参考和 LTR 状态，发送
相应配置/随机访问帧后，解码端清理旧参考并恢复。限制关键帧请求频率，避免拥塞时 I 帧风暴。

接收端重启会改变控制 SSRC，当前发送器绑定首个控制 SSRC，需要明确的新实例/会话协商。
按配置 peer、媒体会话和已启用的认证验证新实例，接受新会话后再清理旧统计与去重缓存；
不能因为任意陌生包到来就解除绑定。若启用现有 HMAC，重启后的索引和重放窗口也必须纳入测试。

重传增加时间期限与预算，只修复仍有用的包；超期时放弃旧数据并走恢复路径。
I 帧可能比普通帧大，恢复允许单独的有限时间预算，但仍受发送限速和内存上限约束。
超过恢复预算时明确报告不可满足，不能异常退出或无限增加队列。

恢复目标建议先按 2 秒评估，计时从**链路已恢复且两端模型已经就绪**开始；不包含上电和模型加载。

## 8. 实施顺序与验收

1. 标定量化档位与实际码量/画质，完成 `target_rate` 固定目标模式，先证明编码器能跟随目标。
2. 补齐带宽统计、能力/会话协商和严格控制校验，接通 codec/pacer 双目标及在途反馈。
3. 启用保守自适应和有界重传，欠带宽时降低量化档位，达到下限后按确认的过载策略处理，
   再联调安全 I 帧恢复。
4. 在双板上做受控限带、丢包和重启测试；双板持续测试需先具备解码板散热条件。

候选验收标准，不将尚未测量的参数写成保证：

- 可跟踪范围内的复杂场景，固定目标模式按 5 秒窗口评估，初始误差目标 ±15%；极低复杂度或
  量化饱和时报告受限状态，不通过无效填充凑足码率。
- 2 Mb/s → 500 kb/s → 2 Mb/s 阶跃：降带宽后初始目标 2 秒内作出有效降码动作；
  稳态达到预算，恢复平滑、不会反复大幅振荡。总发送均值允许误差/突发规则单独记录。
- 正向 RTP/IP、该方向 RTCP 和重传都纳入预算；逆向反馈单独受限。检测帧号始终与视频一致。
- 同一场景、可用带宽充足、相近画质下，对照固定档位吞吐，控制开销初始目标不超过 5%，
  争取保持接近 30 FPS；不能沿用空场景结果保证所有档位/复杂度下均为 30 FPS。
- 验证静止场景、1%/3%/5% 随机丢包、突发丢包、乱序、RTCP 单独中断、RTP 单独中断、
  两板任一进程重启、SSRC/序号回绕、迟到反馈、重复命令、非法 TLV 和可选认证模式。
- 解码参考正确，恢复不等待整个默认 GOP；无无限排队、越界、假 ACK 或不可退出的等待。

限带工具只匹配两板间 RTP/RTCP，PC 流量和管理 SSH 不参与自适应测试预算。
先进行本地模拟和有限帧短测，再评估持续联调，测试中记录真实发送码率而非只看配置值。

| 事项 | 需要的信息/建议 |

| 两板链路码率 | **已确认：暂用 2 Mb/s**，按正向初始/最大通信预算设计；不含 PC 流量。最低可用预算待档位和协议开销标定 |
| 带宽不足时的优先级 | **已确认：降低当前代码的 qp / q_index**；本轮不默认自动降帧或分辨率。最低档位仍不足时，告警/暂停策略待确认 |

### 配置与行为

本地 `configs/encoder.toml` 已启用以下配置。本节记录首版本地实现阶段；随后板上验证见第 11 节。

```toml

min_qp = 0
max_qp = 11
rate_control_mode = "adaptive_rate"
adaptive_max_bitrate_bps = 2000000
adaptive_feedback_timeout_ms = 3000
rtcp_feedback_interval_ms = 500
output_transport_max_queue_delay_ms = 200
```

- `fixed_q` 为固定档位，`target_rate` 配合正值 `target_bitrate_bps` 控制 codec 目标，
  `adaptive_rate` 配合 `adaptive_max_bitrate_bps` 控制两板正向总通信预算。
  旧配置未指定模式时，根据原有目标值推导固定档位或固定目标，保持兼容。
- 当前自动档位范围为 0～11：欠带宽时向下调，恢复时最多回到原有基线 11。
  这个范围是本地初始配置，最低可接受画质和实际可跟随码率仍需板上标定。
- RTP pacer 使用总预算的 97.5%，正向 RTCP 使用剩余约 2.5%，均允许有限突发。
  codec 初始占预算约 85%，再扣除学习到的帧封装、检测、RTP/UDP/IP 和配置刷新开销；
  为修复流量留余量。只有编码输出积压时，codec 比例降到约 65%，不因此继续降低网络预算。
  重传与视频走同一个 pacer。反向 RTCP 独立限额，与 PC 的预览和统计流无关。
- 反馈统计使用相邻有效报告的累计字节/包计数和接收端本地运行时间差，间隔通常约 500 ms，
  不是已实现的 1 秒滑窗。丢失反馈可跨窗口计算；静止画面的低吞吐不解释为低带宽。
  RTT 来自匹配的 SR 记录及 LSR/DLSR，无需同步板卡时钟。
- 每 200 ms 最多检查一次状态；连续两个有效拥塞窗口下调 20%，连续四个稳定窗口后小步上探。
  这几个控制阈值当前为实现常量，反馈周期、反馈超时和队列预算可配置。
- 超过 3 秒无有效反馈时停止升码并逐步降低正值预算。网络下限按一个最大包在队列时间内
  可序列化推导，默认约 50.9 kb/s；这是控制器运行下限，不是链路保证或业务最低画质承诺。
  日志分别标记反馈失联、网络预算触底、编码过预算、接收端积压及 qp 触底。
- 未实现未经确认的自动暂停、自动降低分辨率或主动丢弃已编码 P 帧。最低 qp 仍不能满足预算时，
  背压可能降低实际 FPS，不能保证始终 30 FPS。
- 200 ms 限制正常包队列的准入预算。大 I 帧分包后逐包进入有界队列，不因整帧大于该时间预算而
  直接失败；整帧序列化、上游背压和端到端延迟可能超过 200 ms，不声称已提供严格延迟上限。

### H.264 卡帧的确认原因

统一五路 UI 时漏带了旧 310P UI 已有的时间戳处理，属于本次迁移回归。旧 UI 参数曾包含 `-fps_mode:v passthrough`、`-enc_time_base:v demux`、低缓存选项及较充分的探测窗口；统一版当时缺失这些选项，实际日志出现极高 MB rate、超过 10000 次重复帧和后续解码错误。

对同一条实际 1080P 相机 RTSP 输入同时运行两种参数、各限制输出 90 帧，得到：

| 参数 | 重复帧计数 | 输出时间进度 | 报告 FPS |
| --- | ---: | --- | ---: |
| 修复前统一版 | 14103 | 0.001 s | 无有效稳态值 |
| 补回时间戳直通及低缓存后 | 0 | 3.7 s | 29.61 |

重复帧计数为 FFmpeg 自身统计，不把它等同于已经发送到网络的实际帧数。真实流实验重现了原问题；早先普通离线片段未重现错误的自动帧率估计，因此未将离线实验当作证明。

已恢复 `passthrough` / `demux`、`nobuffer` / `low_delay`，以及 1 秒分析、5 MB 探测上限。不叠加与 passthrough 冲突的 `-r` / `-fpsmax`。此外：

- 媒体 API 确认原图源已离线时，结束本 UI 自建的对应 H.264 子进程，避免保留失去输入或卡住的进程。
- API 暂不可达时不直接推断输入离线，保留已有推流；不处理其他发布者的进程。
- 29 项 Python 回归、3 项 Node 回归通过；修复 EXE 的无桌面后台自检通过。Thor/310P UI 镜像一致。

参数依据：[FFmpeg 官方文档](https://ffmpeg.org/ffmpeg.html)。
